# 虛擬內閣決策裁決報告：3 人 B2B SaaS 後端選型（Go vs Rust）

## 一句話結論
> **強烈推薦 Go（勝率 100%，總分 8.82 vs 4.34）**：在 3 人新創且全熟 Python、一年需拓展 500 家企業客戶的情境下，決定生死的核心矛盾是**交付速度、商業模型驗證與極低的人員替換風險**；Rust 的極限資源與微秒延遲在此量級下屬於「昂貴的過度工程」。

---

## 一、 問題框定與情境約束

- **團隊狀況**：3 人全功能微型團隊，熟悉 Python，缺乏低階系統級語言生產經驗。
- **業務性質**：B2B SaaS 後端（多租戶隔離、報表匯出、企業 SAML/SSO、RBAC 權限、審計日誌與外部 API 整合）。
- **業務目標**：一年內拓展至 500 家企業客戶。
- **負載特徵**：尖峰預估約 200 ~ 1,500 RPS，瓶頸 95% 在關聯式資料庫（Postgres）IO、鎖競爭與外部第三方網路呼叫。
- **硬性約束**：首年最關鍵是活下來並驗證 Product-Market Fit，容錯率極低，禁不起 2~3 個月生產力中斷。

## 三、 穩健度與敏感度分析

- **推薦方案**：`go`
- **中立勝率**：**100%**（Monte Carlo 模擬在權重波動下，Go 全數獲勝）
- **最大後悔決策（Minimax Regret）**：`go`（選擇 Go 的後悔值最低）
- **翻盤臨界點（Tipping Points）**：
  - 只有當 **「資源效率與硬體成本」** 的權重從目前的 **5.0% 暴增至 61.9% 以上** 時，推薦方案才會逆轉為 `rust`。
  - 這意味著除非產品性質轉變為高頻交易撮合、百萬 QPS 邊緣代理或記憶體嚴格限制在 16MB 的極限計算，否則在所有商業條件下 Go 均穩操勝券。

### 各辯手視角加權結果
- **🛡️ 陳CTO（保守實用派）**：給 Go 8.87 分，給 Rust 3.53 分。最終選擇：`go`。
- **🪓 剃刀（極簡極客）**：給 Go 8.85 分，給 Rust 3.75 分。最終選擇：`go`。
- **⚡ Vex（性能狂熱者）**：給 Go 7.55 分，給 Rust 7.65 分。最終選擇：`rust`（即使性能狂熱者極端偏向效能，Go 分數仍緊咬不放）。

## 四、 關鍵權衡（Trade-offs）

1. **即時交付速度 vs 極限硬體控制力**：
   - 選擇 Go 能確保 Python 團隊在 1~2 週內安全交付生產級代碼並敏捷重構資料模型。
   - 代價是放棄了零 GC 停頓的微秒級尾延遲控制與極限記憶體密度。
2. **人才招募替換韌性 vs 編譯期絕對安全護城河**：
   - 選擇 Go 具備廣闊招聘池與低 Bus Factor 替換風險，對 3 人團隊抗離職風險至關重要。
   - 代價是放棄由 Rust 編譯器杜絕空指標與資料競爭的靜態保障，需依賴規範、Linter 與測試。
3. **開箱即用企業生態 vs 底層無抽象損耗掌控度**：
   - Go 在企業 SAML/SSO、Audit Log、主流 ORM 與雲原生 SDK 成熟完備，避免重複造輪子。
   - 代價是缺乏 Rust 在底層計算密集型與嵌入式場景下的零成本抽象優勢。

---

## 五、 盲點獵人指出的隱形風險

1. **可觀測性與分散式追蹤建置成本（High）**：
   Go 內建 pprof 且 OpenTelemetry/APM 支援成熟；Rust 非同步 tracing 在跨 runtime 追蹤與特定 APM（Datadog/NewRelic）整合較繁瑣，易讓 3 人團隊在線上排錯時耗費過多人力。
2. **故障模式與非同步執行時的崩潰隔離（High）**：
   Rust Tokio 遇到阻塞式 IO 易引發線程飢餓與雪崩；Go 搶佔式排程對初學者容錯度顯著較高。Python 工程師轉型極易誤調用阻塞操作，Go 具備更強的容錯防禦邊界。
3. **資料模型頻繁變更的重構摩擦力（High）**：
   B2B SaaS 早期 Schema 每週更迭，Go 組合式結構體重構迅速，Rust 生命週期與所有權易牽一髮動全身，大幅拉長探索 PMF 的週期。
4. **被質疑的預設假設（Challenged Assumption）**：
   - *真的需要放棄 Python 重寫嗎？* 尖峰 1,500 RPS 對現代非同步 Python（FastAPI + uvloop + asyncpg）搭配適當擴展完全足夠。在尚未驗證 500 家企客的付費意願前重寫，需警惕「過早最佳化」。

## 六、 未解爭議與下一步驗證實驗

### 未解爭議
- **Go GC 與逃逸分析在高並發下是否構成 B2B SLA 致命風險**：
  Vex 主張 Go 逃逸分析與 GC 停頓是破壞企客尾延遲的隱形地雷；陳CTO與剃刀主張 1,500 RPS 瓶頸全在資料庫，Go 的毫秒級 GC 不影響商業交付。

### 建議立即執行的驗證實驗（Low Effort）
1. **實驗一：典型 B2B 業務端點雙語言開發 POC（預估 2 人天）**
   - **內容**：由現有團隊用 Go (Gin) 與 Rust (Axum) 分別實作一條包含 JWT 驗證、Postgres 事務讀寫與外部 Webhook 的真實業務端點。
   - **決定**：精確量化團隊的學習阻力、程式碼可讀性與重構耗時。
2. **實驗二：1,500 RPS 混合負載與 GC 延遲壓測（預估 1 人天）**
   - **內容**：在容器中模擬 1,500 RPS，掛載 50ms 延遲的 Mock DB，監控 Go 的 GC pause 與 p99 尾延遲。
   - **決定**：驗證 Go GC 是否真會在該負載下引發企客 SLA 違約。
